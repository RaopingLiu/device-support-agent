# 架构与面试讲解

这是当前代码的解释。验证结论另见《验证记录》，不能用设计解释代替完成证据。

## 请求到底怎么走

用户输入发送至 `POST /api/sessions/{id}/messages`。FastAPI 校验消息和会话，取得会话锁，把用户消息写入业务库，再调用 `Assistant.run`。

LangGraph 从 `checkpoints.db` 加载该会话的消息状态。模型节点通过 LangChain 发送工具描述与上下文；模型可以直接回答，也可以返回工具调用。返回工具调用时进入工具节点，程序检查白名单与预算、执行 Python 函数，把结构化结果包装为 ToolMessage，再交回模型。每个回合最多执行 8 次工具调用。

最后程序核对引用的片段 ID，返回回答、来源、设备查询结果和当前有效草稿。页面中的设备依据与官方资料分开展示。API 的 trace 字段保留工具调用证据，用于验证是否真的执行了 SQL 或 RAG。

## 为什么用 SQL 和向量库两种数据源

SQL 回答精确事实：某个编号对应什么型号、部署在哪个站点、上联设备是什么、模拟状态记录是什么。查询工具使用固定参数化 SQL，避免把设备编号做成模糊语义检索。

Milvus 回答资料定位：用户的自然语言问题对应哪些技术文档片段。问题经过本地多语言模型向量化，按设备类型和适用范围过滤后检索。返回内容由模型组织，但具体设备现状仍以 SQL 结果为准。

型号存在于 SQL 和文档元数据中：前者是设备属于哪个型号，后者是资料适用于哪些产品。未知型号不默认套用现有厂商的资料。

## LangGraph 的实际作用

当前实现是受控的模型/工具循环，具有真实条件边、持久化状态、工具调用预算。它没有为每一种意图写一个独立节点，也没有增加多 Agent。

等待用户时结束 HTTP 请求。新消息使用相同会话标识重新加载检查点。这种跨回合持久化与 LangGraph interrupt/resume 是不同概念，未验证后者就不称为已实现 interrupt 恢复。

## 为什么工单创建不能全交给模型

模型只拥有生成草稿工具，没有正式创建工具。用户点击明确确认按钮时，浏览器提交草稿编号和版本，后端检查会话归属、状态与版本。在 SQLite 事务内创建正式工单、写关联设备、标记草稿已提交。

同一草稿有唯一约束。重复确认相同版本返回已有工单；确认旧版本、取消后再确认均拒绝。数据持久化成功后才能说创建成功。业务数据库是工单结果的权威来源，不能仅根据模型文字或旧对话判断。

## 模拟案例为什么绑定会话

同一台设备在正常案例、AP 离线案例、上联异常案例中可以有不同的快照。scenario_id 从会话注入工具，不让模型随意切换。这样演示和测试可复现，也不会一个用户切换案例影响其他会话。

设备 offline / unknown 时，无法确认的指标返回 null / unknown；不把旧值或默认值当作当前测量。状态和时间都属于模拟记录，不称为实际实时监控。

## 目前能讲和不能讲的内容

可根据验证记录说明：独立主程序环境、真实模型工具调用、SQL 查询、Milvus 入库检索、引用、工单确认与测试。项目由 AI 辅助实现，应能解释以上调用链与核心设计。

不能宣称：生产部署、真实企业用户、真实设备接入、运营商级网络诊断、大规模性能、覆盖所有型号、自动修复、已通知真实运维人员。站点与设备数字是生成的演示规模，不是业务成效指标。

六篇官方资料加自建 SOP 是最小语料。选择 Milvus 是为了实践独立向量服务及入库/过滤/检索流程，不代表此规模只能用 Milvus。更大规模和更高准确率需要独立评测。
